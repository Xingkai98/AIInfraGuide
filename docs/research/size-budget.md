> Ticket: [Xingkai98/AIInfraGuide#9](https://github.com/Xingkai98/AIInfraGuide/issues/9)
> 回答：一个 lab 页面真实占多少体积，站点扛不扛得住；D01（自包含程度）怎么定。
> 所有数字为实测（KaTeX 0.16.45，与 `package-lock.json` 里 `rehype-katex` 传递解析到的版本一致）。
> 复现脚本见 [`scripts/`](./scripts/)，一图流见 [`scripts/README.md`](./scripts/README.md)。

**结论先行**：站点完全扛得住，而且比设计文档担心的宽裕得多。D01 选 **A（共享 assets）**，
同时把 `--inline` 打包脚本做掉。理由不是"体积不够用"——实测方案 A 和 B 的**首次访问体积几乎完全相同**——
而是方案 A 的第二次及以后每次访问只要 **5.7 KB**，方案 B 每次都要 **265 KB**，21 个 lab 累计差 **14.7 倍**。

## 一、KaTeX 实际开销

### 1.1 核心资产

| 文件 | 原始 | gzip | 说明 |
|---|---:|---:|---|
| `katex.min.js` | 270,325 B (264 KB) | **75,125 B (73 KB)** | gzip 后缩到 28% |
| `katex.min.css` | 23,804 B (23 KB) | **3,473 B (3.4 KB)** | gzip 后缩到 15% |
| woff2 字体（20 个） | 259,792 B (254 KB) | 259,792 B | 已压缩，gzip 无收益 |
| ttf + woff + woff2 全格式 | 1,076,572 B (1.05 MB) | — | **不要这样 vendor** |

`katex.min.css` 从 23.8 KB 压到 3.4 KB，是因为它绝大部分是重复的 `@font-face` 声明骨架；
`katex.min.js` 压到 28% 是 JS 的常态。

### 1.2 字体：真正需要几个

`katex.min.css` 声明了 **20 个** woff2，但浏览器**只在实际渲染到该字族的字形时才去取**。
所以"该 vendor 哪些字体"不该靠读 CSS 猜。用真 Chromium 量（`scripts/font_probe.py`，统计网络请求）：

| 页面内容 | 实际取到的字体数 | 实际字节 |
|---|---:|---:|
| L06 + L00 的真实公式（7 条公式 + 48 个绑定项） | **3** | 47,920 B (47 KB) |
| 故意铺满 21 个 lab 可能用到的全部构造（`\mathbb` `\mathcal` `\mathsf` `\mathtt`、矩阵、`\bigoplus`、`\underbrace`…，29 条） | **10** | 141,232 B (138 KB) |
| 全量 vendor | 20 | 259,792 B (254 KB) |

真实 lab 内容只拉三个：`KaTeX_Main-Regular`、`KaTeX_Math-Italic`、`KaTeX_Size2-Regular`。
连"最坏情况"那 10 个也只有全量的一半。**只 vendor woff2**（现代浏览器一律只取 woff2），
ttf/woff 是给已消失的 IE 遗留的，带着它们让 vendor 目录白白胖 3 倍。

### 1.3 base64 内联的膨胀——一个反直觉的结果

base64 在**原始字节**上就是 4/3，没有悬念。但站点走 gzip 传输，**该看的是 gzip 之后的比值**，
而这里出现了明显的分化：

| 内容 | 原始 | gzip(原始) | gzip(base64) | base64 的 gzip 税 |
|---|---:|---:|---:|---:|
| `katex.min.js`（文本） | 270,325 | 75,125 | 112,784 | **+37,736 B (1.50×)** |
| `katex.min.css`（文本） | 23,804 | 3,473 | 5,563 | +2,104 B (1.61×) |
| woff2 字体（二进制） | 47,920 | 47,953 | 48,355 | **+402 B (1.01×)** |

原因是 gzip 的两套机制分工不同：LZ77 靠找**重复子串**，Huffman 靠**字节频率**。
文本文件的 gzip 收益主要来自 LZ77 的长串匹配，而 base64 把字节流按 6 bit 重新分组，
整个比特流错位，长匹配全部丢失 → 33% 的膨胀原样留在 gzip 输出里。
反过来，woff2 本身已经压缩过，没有可被 LZ77 利用的重复，gzip 本来就只能吃 Huffman 那一口；
base64 的膨胀是**均匀且可预测**的，Huffman 恰好能把它压回去。实测 +402 B，基本免费。

**这条直接决定了 `--inline` 该怎么写**：JS/CSS 以**文本**进 `<script>`/`<style>`，
base64 只留给字体。见 §三 B-smart。

## 二、trace JSON 体积

`scripts/gen_trace.py` 生成仿真轨迹。**说明**：递推是真的（L00 的结果与 `numpy` 的 softmax
断言到 1e-9，L06 断言到精确 softmax），但输入来自定种子 RNG 而非真实模型——
对 R02 关心的"线上字节数"足够，schema 按设计文档 §一 的数据模型写。

| Lab | 精度 | 布局 | 原始 | gzip |
|---|---|---:|---:|---:|
| **L06 FlashAttention**<br>`N=8, d=16, Br=4, Bc=4`，4 step | full | compact | 29,780 | 9,172 |
| | **sig6** | **compact** | **16,739** | **4,642** |
| | sig6 | pretty | 43,491 | 5,468 |
| | dec4 | compact | 14,122 | 3,630 |
| **L00 Online Softmax**<br>`N=8, Bc=4`，3 step | full | compact | 3,573 | 1,290 |
| | **sig6** | **compact** | **2,934** | **1,112** |
| | sig6 | pretty | 5,592 | 1,247 |
| | dec4 | compact | 2,815 | 1,052 |

几个可操作的结论：

- **trace 根本不是瓶颈。** L06 最大的情况（full + pretty + 4 步全量 dump）也才 56 KB 原始 / 10 KB gzip。
  相对 KaTeX 的 254 KB 字体，它是零头。设计文档把注意力放在 trace 上是错配的。
- **精度可选 sig6**（6 位有效数字），相对 full 省 44% 原始、49% gzip，而 6 位对肉眼可读的张量完全够。
- **不要 pretty print**：缩进让原始体积涨 2.6 倍、gzip 涨 18%，没有任何读者看得见它。
- **不做去重也够用**：L06 每步 dump 7 张张量、零冗余（0% 可去重），已经是紧凑的；
  L00 有 32% 是重复的 `x`，但绝对值只有 210 B，不值得为它加一层引用机制。

## 三、单页总体积：方案 A vs 方案 B

引擎按设计文档 §四 的 30–60 KB 取值，合成 46 KB 的 vanilla JS 源码占位
（这是**占位值，不是真实引擎**——`labs/engine/` 还不存在，P0 落地后需复测）。

### 3.1 主表（引擎 46 KB，字体取 12 个"常见"子集）

| 组件 | 原始 | A 的线上字节 | B 的线上字节（正确内联） | B 的线上字节（全 base64） |
|---|---:|---:|---:|---:|
| `index.html`（骨架 + 正文） | 848 | 589 | 589 | 589 |
| `katex.min.js` | 270,325 | 75,048 | 75,048 | 112,784 |
| `katex.min.css` | 23,804 | 3,459 | 3,459 | 5,563 |
| `engine.js` | 46,105 | 13,565 | 13,565 | 18,013 |
| `L06.trace.json`（sig6） | 16,739 | 4,642 | 4,642 | 4,642 |
| fonts（12 × woff2） | 172,416 | 172,311 | 173,836 | 173,836 |
| **合计** | | **269,614 B (263 KB)** | **271,139 B (265 KB)** | **315,427 B (308 KB)** |
| **HTTP 请求数** | | 17 | **1** | 1 |

即：**方案 B 正确内联后，首次访问 265 KB，与方案 A 的 263 KB 只差 0.6%——基本是平手。**
设计文档设想的"B 更重"，只有在**把 JS/CSS 也 base64** 时才成立（308 KB，+17%）。

### 3.2 加上第 1.2 节的字体实测后

| 字体策略 | A 首次 | B 单文件（原始 / gzip） | 第二次访问起（A） |
|---|---:|---:|---:|
| 实测真实内容（3 个） | **145 KB** | 412 KB / **142 KB** | **5.7 KB** |
| 实测最坏情况（10 个） | 233 KB | 533 KB / **234 KB** | **5.7 KB** |
| 全量 20 个 | 349 KB | 688 KB / **351 KB** | **5.7 KB** |

**只 vendor 真实用到的字体，比 A/B 之争本身更值钱**——把首次访问从 263 KB 砍到 145 KB，
省下的比"选 A 还是选 B"多得多。

### 3.3 与设计文档的 1.5 MB 估算对比

文档 §四 说 B "单页约 1.5MB"。实测复现出这个数字的来源：

```
katex.min.js  base64            360,436
katex.min.css base64             31,740
字体 ttf+woff+woff2 base64    1,435,432   ← 关键
                               ---------
                               1,827,608 B = 1.83 MB
```

两个错误叠加导致高估：
1. **带上了 ttf 和 woff**——浏览器只取 woff2，另外两种格式一个字节都不会下载。这一项就占 2.47 倍。
2. **全部 base64**——JS（文本）base64 后 gzip 多花 50%，应当按文本内联。

修正后：**574 KB 原始 / 268 KB gzip**（12 字体），或 **412 KB 原始 / 142 KB gzip**（实测 3 字体）。
比文档估的 1.5 MB 小 **2.6–3.6 倍**。

### 3.4 缓存模型——A 的真正优势

实测线上响应头（`curl -I https://caomaolufei.github.io/AIInfraGuide/`）：

```
cache-control: max-age=600
etag: "6ab2407e-b232"
last-modified: Tue, 22 Sep 2026 08:46:54 GMT
age: 150
```

即默认 `max-age=600` + `ETag`/`Last-Modified`。
10 分钟内直接命中内存/磁盘缓存；10 分钟后走条件请求，用 `If-None-Match` 命中则 `304`，只付请求头。

- 方案 A：**首次 263 KB，之后每个 lab ~5.7 KB**（新的 HTML 骨架 + 新的 trace + 十几个 304 头；
  5.7 KB = 实测骨架 589 B + trace 4,642 B + 约 600 B 的条件请求/响应头开销）。
- 方案 B：**每个 lab 都是 265 KB**，没有任何东西可缓存——单文件里连引擎都随页面重发。

| 场景 | 方案 A | 方案 B | 倍数 |
|---|---:|---:|---:|
| 1 个 lab | 263 KB | 265 KB | 1.0× |
| 3 个 lab | 275 KB | 795 KB | 2.9× |
| 21 个 lab | **377 KB** | **5.5 MB** | **14.7×** |

用实测 3 字体重算：A **256 KB**（145 KB + 20×5.7 KB） vs B **2.9 MB**（21×142 KB），11.5×。
**这才是选 A 的决定性理由。**

## 五、Pagefind 对 lab 页面的行为

担心是"`public/labs/` 下的大 HTML 会不会让索引膨胀或变慢"。实测：**完全不会，而且是字节级不变。**

把两个页面种进 `dist/labs/` 做 A/B 对照——一个是方案 A 的 17,374 B 页面，
一个是方案 B 的 587,313 B 单文件巨页，**两者正文文字完全相同**：

| | 索引页数 | 索引词数 | 索引体积 |
|---|---:|---:|---:|
| 种植前 | 353 | 12,558 | 3,012,382 B |
| 种植后（+2 个 lab） | 355 | 12,572 (**+14**) | 3,013,326 B (**+944 B, +0.03%**) |

再做单页隔离测试更清楚：

| 单页 | 文件大小 | Pagefind 提取词数 | 索引产物 |
|---|---:|---:|---:|
| 方案 A 页面 | 17,374 B | 14 | 448 B |
| 方案 B 单文件 | 587,313 B | 14 | 448 B |

**逐字节相同。** 原因：Pagefind 只索引正文文本，主动跳过 `<script>` 和 `<style>`——
base64 内联的引擎和字体对它完全不可见。

**结论：Pagefind 对 D01 是中立的，不构成任何一方的理由。** 之前"大 HTML 会让索引膨胀"
的担心可以排除。构建耗时上，355 页 2.1 s vs 353 页 2.8 s，在噪声范围内。

- **不建议走 LFS**：Pages 不服务 LFS 里的文件。本项目也没有大到需要它的文件。

## 七、对 D01 的推荐

### 选 **A（共享 assets 目录）**，并把 `--inline` 打包脚本一起做掉。

**为什么 A 而不是 B**

1. **B 唯一的卖点在尺寸上不成立。** 正确内联后 B 首次访问 265 KB，A 是 263 KB——0.6% 的差别。
   设计文档"B 代价是单页约 1.5 MB"的担心，实测修正后是 265 KB（见 §3.3）。
2. **A 的第二次访问只要 5.7 KB，B 永远要 265 KB。** 21 个 lab 累计 A 377 KB vs B 5.5 MB，**14.7 倍**。
   读者越是认真用这个站点（看得越多），差距越大——而这恰恰是我们想要的行为。
3. **A 已经满足离线需求。** 设计文档 §四 对 A 的描述是"整包拷走即可离线打开"，
   这是对的：相对路径在 `file://` 下正常工作。B 额外提供的只是"分享**一个**文件"，
   这个窄场景用 `--inline` 按需生成即可，不必让 21 个页面都为此付出 14.7 倍的代价。
4. **Pagefind 中立**（§五，逐字节相同），这条不能用来支持任何一方。
5. **仓库小 8 倍**：1.5 MB vs 12 MB。
6. **修一次引擎 bug 只改一个文件**，而不是重新生成 21 个内联页面。

**`--inline` 脚本值得做，但要按 §1.3 的结论写"聪明版"**

它不是"锦上添花"，而是**必须以正确方式实现**——否则会凭空多花 17% 的流量：

- JS / CSS / trace 以**文本**内联进 `<script>` / `<style>`，**不要 base64**。
- base64 **只用于字体**——对已压缩的 woff2，gzip 后 base64 仅 +1%，基本免费。
- 全 base64 的"朴素版"实测 308 KB，比正确版多 **17%**，纯浪费。

工作量很小（一个读 HTML、替换 asset 引用、写单文件的脚本，约 50 行），
但它把"单文件分享"从一个**全站架构决策**降级成一个**按需执行的构建步骤**——
这正是它该待的位置。

**顺带做掉、收益可能超过 A/B 本身的两件事**

1. **只 vendor woff2，不要 ttf/woff。** 现代浏览器只取 woff2；带上另外两种格式让 vendor 目录胖 3 倍。
2. **字体按实测裁剪。** 真实 lab 内容触发 3 个字体（47 KB），最坏情况 10 个（138 KB），
   全量 20 个（254 KB）。取"真实内容 + 一档余量"即可。**这一项把首次访问从 263 KB 降到 ~145 KB，
   比 A/B 之争省得多。**

### 给实现的三条硬性约束

- trace 用 **sig6 + compact**（不要 pretty）：L06 = 16.7 KB 原始 / 4.6 KB gzip。留一个精度开关便于调试。
- `katex.min.css` 记得走 gzip——它 23.8 KB 压到 3.4 KB，是全站最高压缩比的文件。
- ⚠️ **P0 引擎落地后必须复测本报告。** 本文的 46 KB 引擎是合成的占位值（gzip 13.5 KB 是代理值）。
  真实引擎若显著超出设计文档的 30–60 KB 预期，§三 的绝对数字要更新——但
  **A vs B 的结论不会变**，因为它由缓存结构决定，与引擎具体大小无关。

## 八、一句话回答 ticket 的问题

**扛得住，而且宽裕得多。** 一个 lab 页面首次访问 263 KB gzip（现有最大页已是 76 KB gzip），
21 个 lab 全上也不到发布站点预算的 1.5%。站点真正的问题不是体积，是**缓存结构**——
选 A 让每个后续 lab 只要 5.7 KB，选 B 让每个都要 265 KB。
D01 选 **A**，`--inline` 按需做且必须用"文本内联 JS/CSS、base64 只给字体"的聪明写法。
