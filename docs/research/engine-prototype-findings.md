四个问题各自的结论，以及**被推翻的假设**：

| 问题 | 结论 | 关键证据 |

| 1 时间轴任意跳转 | **成立，不需要反向操作** | 28 次跳转（含完全逆序、乱序回环）0 次不一致；对照组（有状态播放器）17 次不一致 |
| 2 轨迹契约 | **基本够用，但缺 2 个字段**（`tensors[].init`、slot 值的类型区分）；`kind` 有用但语义没定死 | lint 对干净的 trace 报 0 gap，对故意破坏的副本报 11 个 |

| 4 DAG 布局 | **10 节点可读；但自研分层布局必须补"顺序边"，否则 20 节点以上就废掉** | 42 节点：无顺序边 maxc=11 画布 1536×380 一团乱麻；有顺序边 maxc=1，折行后干净可读 |

**三个最重要的产出**（都比"验证成功"更值钱）：

1. **契约缺 `tensors[].init`。** 没有任何 step 写 `x`，`render(trace, 0)` 根本不知道输入是什么。D06 草案的 `tensors` 只有 `shape/dtype/label`，没有值。不补这个字段，纯函数重建从第一步起就是错的。
2. **"只更新数值 span 的 textContent" 不可行。** 因为触发数值替换的**恰恰是符号式公式**（`\max_i x^{(j)}_i` 这类下标在符号档就已经是具体值了），它本身就是 LaTeX。`textContent = "0.83"` 没问题，`textContent = "\max_i x^{(2)}_i"` 会把反斜杠原样打到屏幕上——**原型里真出现了**（截图 `07` 改前的版本显示 `\left[1.4, 0.35\right]`）。正确做法见问题 3。
3. **DAG 必须补"顺序边"。** 只按数据依赖分层，`load` 这类"只读不写、无前驱"的步骤会被留在第 0 层，层宽随块数线性增长（10→74 节点时 maxc 从 3 涨到 19），画布变成 8:1 的横条。

## 问题 1 · 时间轴任意跳转

### 设计假设

纯函数 `render(trace, i)`：每个张量的值 = "≤ i 的最大写入步" 的那个值；不顺序播放、不累积。

### 验证方法

原型里 `resolveState(trace, i)` 就是这个纯函数。把它和一份**顺序累积的基准**（走一遍，每步 `Object.assign` 上去）逐步对比：

- 正向 0→9
- **完全逆序** 9→0
- 跳回 / 跳到尾 / 乱序回环：`5→1`、`1→0`、`0→9`、`9→3`、原地 `3→3`、`3→5`、`5→2`、`2→5`

**对照组（关键）**：同时跑一个"故意做错"的有状态播放器——只保留一个可变状态对象，跳转时直接把目标步的 `state` 盖上去，从不回读更早的步骤。这是纯函数设计要防的那个失败模式。

### 实测结果

```
纯函数重建：28 次跳转（正向 / 完全逆序 / 跳回 / 乱序回环），0 次不一致——与顺序累积基准逐位相同。
对照组（故意做错的有状态播放器）：同一批跳转里 17 次不一致。
```

（在页面上点「重新运行」可见；整页截图 `15-selfcheck-perf.png`。）

**对照组真的会翻车**，所以那个 0 不是"测试写错了"。这比单纯报一个绿灯重要得多——没有对照组的"全部通过"是不可信的。

### 有没有"累积性、无法从静态快照重建"的字段？

在**这条 trace 里没有**。所有状态量（`m`/`l`/`acc`/`x_blk`/`O`）都是**整量覆盖写**：`step.state` 里放的是写完之后完整的新值，不是增量。所以回溯 = "取 ≤i 的最后一个写"，无需回滚任何副作用。

页面上「C 段」把这件事拆成一张表，逐项列出**能**和**不能**重建的量。真实存在的两个"不能"：

| 量 | 能否重建 | 说明 |
|---|---|---|
| `m / l / acc / x_blk / O` | 能 | 整量覆盖写 |
| 已走过的路径（节点三态） | 能 | 就是 step 索引的序关系，不用存 |
| 修正因子 `e^(m_old−m_new)` | 能，但**只因为 trace 显式给了它** | 它是 `\region{CORR}` + `step.regions`。值本身可由 `m_old`/`m_new` 算出，但引擎要"高亮它"就得有个地方取 |
| **`x` 的原始值** | **不能** | 没有任何 step 写 `x`。**这就是契约缺口，见问题 2** |
| "上一次是谁写的这个张量" | 不能（除非引擎自己扫） | 值能重建，**来源步**不能——除非引擎自己回扫（本原型就是这么做的，O(steps)）。若要显示 provenance 又不愿重扫，trace 得给 per-step 的写集 |

### 结论：**不需要记录反向操作**，但有一个前提条件

需要反向操作的**唯一情形**是：某状态量是**非幂等的累积**（append 到列表、计数器 `++`、引用计数、不可逆的指针推进）。这时只要 `step.state` 记的是**累积后的新全量**（像本原型的 `l`/`acc` 那样），纯函数重建照样成立——**契约要求的是"记全量"而不是"记 delta"**，这一点必须在 D06 里写死。

真正的风险落在**后续 lab**：

- **L05 KV Cache / L09 PagedAttention** —— KV cache 是逐 token 追加，块池是分配/回收。如果那类 lab 在 trace 里按步记全量快照，代价是 O(N²) 的 JSON 体积；记 delta 就必须有反向操作。
- **建议**：D06 不要现在就为它们定反向操作的表示，而是**给个逃生舱**——保留一个 per-step 的 `inverse` 或 `snapshot` 可选字段，等 L05/L09 真正开工时再定。本原型能证明的是：**P0 的 L00 不需要，别为了它给所有 lab 增加复杂度。**

## 问题 2 · 轨迹契约够不够用

### 方法

按 D06 草案手写一份最小 trace（1-D online softmax，`x ∈ R⁴`，`Bc = 2`，2 个块，10 个 step），并且**不迁就引擎**——该用 `\max_i x^{(j)}_i` 这种带下标的公式就用。

然后写了一个 **lint**（`engine.js` 的 `lint()`）对着草案逐条查：读写一致性、graph/steps 一致性、三档完整性、三元组形状、`state` 里的未声明张量、narration 里混入 LaTeX。

**lint 有效性对照（关键）**：同时 lint 一份**故意破坏的副本**（删掉 `tensors.x.init`、塞入 `NaN`、删掉一个 `\slot` 引用、把三元组降成二元组）。干净的报 0 gap，破坏的报 11 个问题——证明这个 0 不是 lint 永远报 0。

### 契约需要补的字段（给 I01 的直接输入）

**① `tensors[].init`（必补，硬缺口）**

```jsonc
"x": { "shape": [4], "dtype": "fp32", "at": "HBM", "role": "input",
       "init": [0.83, -0.20, 1.40, 0.35] }   // ← 补这个
```

没有任何 step 写 `x`，但 `ld1` 读它。没有 `init`，`render(trace, 0)` 就不知道输入是什么，页面上那块显示"— 本步之前无值 —"。这是**纯函数重建的必要条件**：每个被读的张量必须有一条"初始值"来源，要么来自 `init`，要么来自某个更早 step 的 `state`。

**② slot 值的"类型"要能区分（必补，或者约定死）**

绑定值是 LaTeX，还是纯文本？原型里踩了两次：

- `VALS: "\left[1.4, 0.35\right]"` —— 是 LaTeX，直接 `textContent` 会显示成字面反斜杠
- `MOLD: "-∞"` / `"0.83"` —— 是文本，直接 `textContent` 正好

**原型里的处理**：一律当 LaTeX 交给 KaTeX 渲（`0.83` 在数学模式下渲染正常）。所以**约定可以是"slot 值一律是 LaTeX 片段"**，但这条要**明写进 D06**；否则 trace 作者随手写 `1/2` 会拿到一个斜体分数，写 `a_b` 会拿到下标。另外 `-∞` 必须写成 `-\infty`。

> **相关坑（已写进 `make_trace.py` 注释）**：`NaN` / `±Infinity` **不是合法 JSON**。`m` 的初始值是 `-∞`。Python 的 `json.dumps` 会输出裸的 `-Infinity` 字面量——这不是合法 JSON，但**恰好是合法 JS**。这正是原型把 trace 存成 `trace.js` 而不是 `trace.json` 的原因。**D06 必须为 ±∞/NaN 定一个哨兵表示**（推荐字符串 `"-\infty"`，或 `null` + 一个有类型的字段），否则 trace 脚本没法把 `m^(0) = -∞` 写出来。lint 会专门报这条。

**③ `kind` 字段到底有没有用？——有用，但语义没定死**

原型真造了一个 `kind: "comm"` 节点（`ld1`/`ld2`「第 N 块载入 SRAM」）。诚实结论：

- **视觉上确实有用**：`comm` 节点在 DAG 上走虚线框 + 紫色圆点，一眼能和 `op` 分开（截图 `03-dag-10-seq-wrap4.png` / `04c-dag-42-seq-wrap6.png`）。
- **但"别扭"的地方是真的**：`ld` 这一步**不写任何标量状态**，所以 `step.state` 是 `{"x_blk": [...]}`——它写的是**中间张量**，而其他 step 写的都是**标量状态**。这暴露了一件事：**`state` 字段混装了两种东西**（"算法状态" vs "中间张量的值"）。原型能跑，因为引擎只把 `state` 当"覆盖写"处理；但 trace 作者会犹豫"`x_blk` 该放 `state` 还是别处"。
- **建议**：`kind` 保留，但 D06 要补一句语义——`state` 是"这一步之后**所有**发生变化的张量值（含中间张量）"，`reads`/`writes` 是**同义的声明**（引擎目前信 `state`，`writes` 只用于高亮）。另外 `alloc`（PagedAttention 分配物理块）那类"改的是外部资源、不是张量"的 step，`state` 该写什么，D06 现在没有答案——**这是留给 L09 的真问题，不是 P0 的**。

### 哪些字段实际用不上

- **`graph.edges[].tensor`**：原型只拿它画边标签（`m` / `l` / `acc` / `x_blk` 4 种取值）。如果边标签对教学不必要，可以省；但原型里它确实让图好读了不少，建议留。
- **`meta.source` / `meta.reference`**：引擎没用，纯给人看。留着无害。
- **`tensors[].dtype`**：原型没用上（没有真去解释 fp32）。L18 量化那个 lab 会用上。

### 用不上的 `\slot` 也会被抓

lint 还报了一条 warning：`步骤 "l1" 的绑定 "BLKMAX" 没被任何档位引用`——**这是真的**，`l` 的公式里确实不需要 `BLKMAX`。虽然无害，但说明 lint 能帮 trace 作者发现冗余。

## 问题 3 · KaTeX 三档切换怎么实现最省事

### 先说被推翻的那个说法

设计文档 §四和 D07 都写：「公式拆成**静态骨架 + 动态数值 span**，拖动时间轴时**只更新数值文本**，不重跑 KaTeX」。

**原型实测：这个描述是错的，直接照做会在屏幕上打出 LaTeX 源码。**

原因是**触发数值替换的恰恰是符号式公式**。看 `m` 的更新：

- 符号档：`m^{(j)} = \max\left(\slot{MOLD},\; \slot{BLKMAX}\right)`
- 数值档：`m^{(j)} = \max\left(-\infty,\; 0.83\right) = 0.83`

`\slot{BLKMAX}` 在**符号档**就要替换成 `\max_i x^{(j)}_i`——**这本身是 LaTeX，不是文本**。同理 `\slot{MOLD}` 在符号档是 `m^{(j-1)}`。所以"只更新数值文本"只在数值档成立，符号档和索引档必须**重新渲染 LaTeX**。

原型里真的踩了这个坑：改之前，第 5 步的公式在屏幕上显示成

```
x^{(2)} ← HBM[x][2:4] = \left[1.4, 0.35\right]      ← 反斜杠原样打了出来
```

该 bug 已在原型里修掉；当前正确渲染见 `07-formula-num.png` 与放大裁图 `17-crop-formula-vals.png`（`[0.83, −0.2]` 正常显示）。

### 正确的做法（已验证）

**骨架按"步骤 × 档位"构建一次；每次游标移动时，只对每个 slot 的值单独跑一次小 KaTeX 渲染。**

```js
// 主公式：展开 \slot{X} -> \htmlId{slot-X}{\phantom{<该 slot 这一档的宽度>}}
// 用该 step 的 num 档值做 \phantom 垫宽，所以换值不会引起公式重排
const html = katex.renderToString(expand(step.formula[tier], pad),
                                  {trust: true, output: 'html'});
// 之后每帧：每个 slot 单独渲染，塞进 KaTeX 自己生成的 <span id="slot-X">
sp.innerHTML = katex.renderToString(binding[tier], {throwOnError: true});
```

三个**实测出来**的关键细节：

1. **`\htmlId` / `\htmlClass` 必须配 `trust: true`**，否则 KaTeX 会静默不生成元素（原型里报了一堆 `Undefined control sequence: \htmlId`）。
2. **不要用 KaTeX 的 macro 回调去拿两个花括号参数**。KaTeX 交回来的参数是**已经反序的词法 token 列表**（实测：`\slot{MOLD}` 到手是单个 token `"DLOM"`），多 token 的 body 会被搅烂。改成**自己写预处理**（`expand()`，花括号配对扫描），可控且好调。
3. **`\region{K}{...}` 的内容里常常嵌 `\slot{...}`**（修正因子就是 `\region{CORR}{\exp(\slot{MOLD} - \slot{MNEW})}`），预处理必须**递归进 region body**。第一版没递归，直接报 `Undefined control sequence: \slot`。

修正因子的高亮（L00 的「修正因子放大器」）就用 `\htmlClass{region-CORR}{...}`，KaTeX 自己会在那个 span 上打出 class，加个 CSS 边框即可——**不需要 Range / surroundContents 那套 DOM 手术**（原型第一版用了 `range.surroundContents()`，跨 KaTeX 的 span 边界时**必然抛 `InvalidStateError`**，这条死路已排除）。截图 `16-crop-formula-region.png` 里 `exp(-∞−0.83)` 被粉色框住，就是它。

### 性能实测（数字来自页面上的真跑，Chromium 148）

页面上点「跑性能实测」重算。下表是**连跑 5 次的中位数**（A/B 的倍数在单次之间有 29×–113× 的抖动，所以这里给区间而不是一个漂亮数字）：

```
                                          中位数     (最小–最大)      含义
A: 全量 renderToString + DOM 挂载          0.35 ms   (0.34–0.76)   朴素播放器每帧付这个
B: 骨架复用 + 只重渲 slot 子公式           0.008 ms  (0.007–0.012) 拆分方案每帧付这个
C: 构建一个骨架（每步一次）                0.35 ms   (0.33–0.40)
D: 重建张量面板（DOM）                     0.057 ms  (0.053–0.087)
E: 重绘 DAG（innerHTML 重建整个 SVG）      0.47 ms   (0.43–0.58)
```

A / B ≈ **30–110×**。但注意右边那列的量级。

公式长度 vs 全量渲染耗时（把第 5 步的公式重复 N 遍）：

```
   1× → 0.39 ms    4× → 1.21 ms     16× → 4.42 ms
   2× → 0.85 ms    8× → 2.90 ms     32× → 9.21 ms
```

### 结论：**拆分方案可行，但它的理由不是性能**

- 全量渲染 **0.35 ms/帧**，只占 60fps 预算（16.7 ms）的 **2%**。**即使每帧全量重跑 KaTeX 也不会卡。** 原设计文档担心的问题**不存在**。
- KaTeX 耗时**随公式长度大致线性增长**（32× 长度 → 9 ms），只有当某条公式长到约 50 倍才逼近预算。P0–P4 的公式都不在这个量级。
- **真正的大头是 DOM**：重绘 DAG（`innerHTML` 重建整个 SVG）0.47 ms + 张量面板 0.06 ms ≈ **0.53 ms/帧，比 KaTeX 全量渲染（0.35 ms）还大**。优化精力应该花在这里（增量更新 DOM class，而不是重建），**不是花在 KaTeX 上**。

**给 I01 的建议**：不要为了性能做骨架拆分。要做的话，理由应该是**它顺带解决了 `\region` 高亮**（KaTeX 生成带 class 的元素，比事后 DOM 手术干净得多）。如果 `\region` 高亮用别的方式实现（比如干脆不框、只用文字说明），那**每帧全量重渲 KaTeX 是最简单且够快的方案**——少一层状态，少一类 bug。本原型建议**先按全量渲染写，把 `\region` 高亮作为唯一需要拆分的理由保留**。

## 问题 4 · DAG 布局可行性

### 自研分层布局的实际工作量

不大。核心就是 **Kahn 拓扑排序求"最长路径深度"当层号**，同层按序排开。原型里 `layout()` 约 50 行（含折行），没有引任何库。**工作量约半天**，不是风险点。

### 但有一个必须补的东西：**顺序边**

只按 `graph.edges`（数据依赖）分层，会得到一个**退化**的图。原因：`ld1`/`ld2`（载入 SRAM）**只读 `x`、不写任何被下游读的张量**——它在数据依赖图上是个**孤立的前驱为空**的节点，Kahn 会把它留在**第 0 层**。块数越多，第 0 层越宽：

| 节点数 | 只用数据边 | 补顺序边后 |
|---|---|---|
| 10 | 最宽层 3，共 6 层 | 最宽层 **1**，共 10 层 |
| 26 | 最宽层 7 | 最宽层 **1** |
| 42 | 最宽层 11 | 最宽层 **1** |
| 74 | 最宽层 19 | 最宽层 **1** |

（`最宽层 = 该层节点数`。"顺序边" = 按 trace 顺序补 `step i → step i+1` 的合成边，**只参与分层、不画出来**。）

补了顺序边之后，每一层恰好 1 个节点——因为算法本身就是一条链。这时再叠一层**折行**（每 N 层折一段），就得到干净的蛇形图。

**截图对比**（同一份 42 节点合成 trace）：

- `04a-dag-42-noseq-nosplit.png`：6 列 + 11 个游离的 `ld` 节点在左侧排成一条竖线，边在右上角绞成一团。**不可读。**
- `04b-dag-42-seq-nosplit.png`：补顺序边后，单排 42 列 → 画布约 4900×190，**8:1 的横条，屏上每个节点宽约 25px，同样不可读**（只是从"乱"变成了"挤"）。
- `04c-dag-42-seq-wrap6.png`：再折行（每 6 层一段，共 7 段），**1024×633，节点 78px 宽，清晰可读**。这是最终形态。

### 节点数超过多少会开始难看

**在 10 个节点以内，单排（不折行）就能读**——但前提是补了顺序边。10 节点时画布 1024×185，宽高比 5.5:1，塞进 1560px 宽的画布，每个节点 78px 宽，舒服。

- **≤10 节点**：单排可读（截图 `03-dag-10-seq-wrap4.png`）
- **10–26 节点**：单排开始变成横条；折行（每段 4 层）后回到 ~1.6:1（截图 `05-dag-26-seq-wrap4.png`）
- **26–74 节点**：必须折行；每段 6–8 层时画布约 1400×900，比例 ~1.5:1，仍然可读（截图 `06-dag-74-seq-wrap8.png`）

注意这里的节点数是**合成放大**的（把 2 个块复制成 17 个块），只为回答"多少节点开始难看"。真实 lab 的 DAG 节点数应该都在 10–20，**在单排可读的范围内**。

### 弧线边 vs 直线边

- **弧线（`arc`）更好读**，但只对**跨层的长边**有效（比如 `init → a1` 这种跨 3 层的边）。原型里长边走贝塞尔上弓 22px，避开中间节点。
- **同层或相邻层用直线（三次贝塞尔，控制点在水平中线）**更干净——硬拗成弧线反而缠。
- **交互上的取舍**：`arc` 模式在节点多时**容易糊**（截图 `04a-dag-42-noseq-nosplit.png` 里那些长弧线就是主要噪声源）；`straight` 模式更"工程图"，但长边会穿过节点框。
- **建议**：**默认弧线 + 只给跨 ≥2 层的边走上弓**，就是原型现在的做法。折行之后长边基本消失（每段内都是相邻层），弧线的优势也就没那么重要了——**折行才是主要手段，弧线是次要修饰**。

### 三态切换是否顺滑

**顺滑。** 三态就是 `step` 索引和游标的序关系（`< i` 变暗 / `== i` 高亮 / `> i` 虚化），纯 CSS class 切换，带 `transition: opacity .18s`。

实测重绘 DAG（`innerHTML` 重建整个 SVG）**约 0.47 ms/帧**——单帧内完成，肉眼看不出闪烁。不过这是 `innerHTML` 全量重建的代价；真正上 I01 时**建议改增量更新 class**（不重建 DOM），能把 0.47 ms 降到接近 0，顺便解决节点焦点丢失的问题（现在重建会让 Tab 焦点掉掉）。

`kind` 的视觉区分也在这一层。实测的计算样式：

| kind | 节点框 `stroke-dasharray` | 角标圆点 |
|---|---|---|
| `op` | `none`（实线） | `rgb(78,161,255)` 蓝 |
| `comm` | `3px, 2.5px`（虚线） | `rgb(201,140,255)` 紫 |
| `state` | `1px, 2.5px`（点线） | `rgb(95,211,154)` 绿 |

三态同时存在也验证过：停在第 1 步时 DOM 里 `{visited:1, current:1, future:8}`，三态齐全。DAG 节点可 Tab 聚焦、回车跳转（实测：聚焦 step4 按回车 → 跳到「第 4 / 9 步」）。

## 给 I01 的输入清单（按优先级）

**必须补进 D06 契约**：

1. **`tensors[].init`** —— 每个被读的张量必须有初始值来源；否则 `render(trace, 0)` 从第一步就是错的。
2. **±∞ / NaN 的哨兵表示** —— JSON 表示不了 `-Infinity`；原型靠 `json.dumps` 输出裸 `-Infinity`（合法 JS，非法 JSON）绕过，正式版不能这么侥幸。
3. **`step.state` 的语义写死** —— "这一步之后所有发生变化的张量值（含中间张量），**记全量不记 delta**"。这是"不需要反向操作"的前提。
4. **slot 值一律是 LaTeX 片段**（或显式给类型标记）—— 否则 trace 作者写 `1/2` 会拿到斜体分数。

**建议补**：

5. **KaTeX 拆分方案的理由从"性能"改成"`\region` 高亮"** —— 性能实测证明全量重渲只要约 0.35 ms/帧（60fps 预算的 2%），不是瓶颈。为性能做拆分是过度设计。
6. **DAG 分层必须补顺序边**，并给出折行策略（层数 > 10 时每 6–8 层折一段）。
7. **lint 应当作为 trace 脚本的一部分**（Python 侧或 CI 里跑），把本原型的 `lint()` 规则搬过去；`labs/traces/*.py` 输出 JSON 之后立刻自查。

**留给后续 lab 的问题（P0 不用管）**：

8. `kind: "alloc"`（PagedAttention 分配物理块）那类"改外部资源、不改张量"的 step，`state` 写什么？→ L09 定。
9. KV cache 逐 token 追加若不想记全量快照，需要反向操作或 delta——**给 D06 留一个可选 `snapshot`/`inverse` 逃生舱字段，别现在实现**。→ L05/L09 定。
